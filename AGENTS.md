# AGENTS

Этот файл является входной инструкцией для coding agents, которые работают с репозиторием `blind`.

Перед любыми изменениями в проекте агент должен:

1. Сначала изучить структуру текущей задачи и затронутые файлы.
2. Учитывать правила из документации проекта.
3. Не придумывать архитектуру, если она уже зафиксирована в коде или в `docs`.
4. Вносить минимально достаточные изменения без лишних переписываний.
5. Сохранять стиль именования и структуру проекта.

## Обязательные документы проекта

Перед изменениями агент должен обязательно ознакомиться со следующими документами:

- `docs/contributing/sections/codeStyle.md`
- `docs/contributing/sections/gitRule.md`
- `docs/contributing/sections/generateRule.md`
- `docs/contributing/sections/pluginRule.md`
- `docs/architecture/index.md`

Если задача затрагивает конкретную область проекта, агент должен дополнительно открыть и изучить связанные разделы из `docs`, относящиеся к этой области.

Если правила в коде и документации расходятся, агент должен:

1. Не переписывать кодовую базу целиком под документ без явного запроса.
2. Сообщить о расхождении.
3. Предлагать точечные и безопасные изменения.

## Базовые правила работы

1. Не выполнять крупные рефакторы без прямого запроса.
2. Не менять публичные соглашения проекта молча.
3. Не удалять существующие файлы, правила или структуру без необходимости.
4. Если правило неочевидно, сначала проверить `docs`.
5. Если в проекте уже существует локальный паттерн, его нужно уважать.
6. При правках документации не переписывать раздел целиком, если задача касается только части текста.

## Архитектурные ориентиры

Текущая структура проекта строится вокруг следующих областей:

- `src/app` - прикладной слой приложения
- `src/core` - общие переиспользуемые модули
- `src/config` - конфигурация проекта
- `src/assets` - статические ресурсы
- `docs` - документация проекта

## Именование сущностей

Агент должен соблюдать соглашения из `docs/contributing/sections/codeStyle.md`.
Если агент предлагает новую сущность, ее имя должно соответствовать этим правилам.

## Импорты

1. Для файлов из `src` следует использовать алиас `@`, если он уместен в текущем файле.
2. Не создавать длинные и хрупкие относительные импорты без необходимости.
3. Не оставлять неиспользуемые импорты.

## Документация

Если изменение затрагивает соглашения проекта, генерацию, архитектуру или процесс разработки, агент должен проверить, нужно ли обновить документацию в `docs`.

Если агент создает новый важный проектный паттерн, стоит явно отметить, что документация требует обновления.

## Что агенту не стоит делать

- не переписывать документацию целиком без запроса
- не менять принятый нейминг по своему усмотрению
- не смешивать глобальные токены и локальные переменные компонента
- не вводить новые архитектурные слои без необходимости
- не использовать разные стили именования для одинаковых сущностей

## Ожидаемое поведение агента

Хорошее поведение агента в этом проекте:

- сначала читать контекст, потом редактировать
- предлагать точечные изменения
- следовать существующим соглашениям
- явно отмечать риски и несостыковки
- поддерживать документацию в актуальном состоянии, если изменения затрагивают правила проекта

Если после ознакомления с обязательными разделами у агента остаются вопросы, на которые нет ответа в этих документах, он должен:

1. Либо сначала задать уточняющий вопрос перед внесением спорных изменений.
2. Либо самостоятельно найти недостающую информацию в остальной документации `docs`, если это можно сделать надежно и без догадок.
