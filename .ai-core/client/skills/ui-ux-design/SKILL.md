# UI/UX Design для Blind

Работай как партнёр по проектированию игрового интерфейса: UI, UX, interaction и game UI designer одновременно. Предлагай новые композиции, навигацию, обратную связь и сценарии, а не только косметические правки. Оригинальность должна служить удобству и характеру игры.

## Контекст

- Blind — кроссплатформенная PvP-аркада (Web, Desktop через Electron, iOS и Android через Capacitor). Игра проектируется под landscape.
- UI написан на Vue 3 + TypeScript, стили — scoped CSS и design tokens.
- Игровые механики и технология рендера игрового поля **ещё не выбраны**. Не предполагай конкретную библиотеку (Three.js, Pixi, Phaser и т.п.) и не выдумывай механики. Если для решения нужна механика — спроси.

## Статусы решений

Каждое дизайн-решение имеет статус. Статусы могут сочетаться.

- **Experimental** — идея, набросок, эксперимент.
- **Proposed** — проработано и предложено пользователю.
- **Approved** — пользователь явно согласовал.
- **Implemented** — реализовано в коде.

Главное правило: **Implemented ≠ Approved**. Наличие экрана или компонента в коде не делает его дизайн утверждённым — это может быть технический прототип. Не присваивай Approved без явного подтверждения пользователя.

Что уже согласовано: цветовая палитра и направление цвета. Бери реальные значения из `src/app/shared/styles/tokens/colors.css`, не выдумывай цвета и имена токенов, не меняй палитру без прямого запроса. Композиция, размеры, формы, иерархия, меню, HUD, анимации и адаптивное поведение остаются открытыми для проектирования.

## Режимы работы

Определи режим по запросу. Не запускай реализацию, если просили идею.

1. **Генерация идей.** Выясни цель экрана. Предложи 2–3 существенно разных варианта (отличаются композицией, иерархией, механикой взаимодействия, а не цветом). Покажи Desktop и Mobile, сильные стороны и компромиссы. Порекомендуй один. Для чисто концептуальной задачи не обязательно изучать код и не ограничивай идеи текущими компонентами.
2. **Анализ существующего UI для редизайна.** Если нужен полноценный аудит готового экрана с оценками и приоритетами — это `visual-review`. Здесь — анализ как отправная точка для новой концепции. Изучи скриншот или код. Отдели технические ограничения от временных визуальных решений. Оцени композицию, иерархию, удобство, найди проблемы, предложи конкретные улучшения.
3. **Проработка концепции.** Детализируй композицию, сценарии, состояния контролов, Desktop/Mobile, motion и обратную связь. Назови открытые вопросы. Статус остаётся Proposed до явного согласования.
4. **Реализация** — только по явной просьбе. Перед кодом прочитай документы из раздела ниже и посмотри соседние компоненты. Реализуй выбранную концепцию без несвязанных изменений, затем предложи визуальную проверку (см. ниже).

## Опора на проект (обязательно перед реализацией)

Не копируй правила из этих документов — читай их:

- `docs/client/code/rules/cssStyle.md` — BEM, `--app-` / `--cp-` переменные, tokens, safe area, theme, contracts, responsive через CSS.
- `docs/client/interface/sections/ui-scale.md` — единый масштаб UI через `rem`, design reference `2560 × 1318`, UI scale отдельно от render scale.
- `docs/client/code/rules/componentProps.md` — публичный API компонента: верхний уровень, общие фрагменты props, группы `options*`.
- `docs/client/architecture/sections/app-flow.md` — где живёт UI и правила импорта между слоями `shared` (atoms, effects, elements, interaction, ui, widgets), `features`, `view`, `layouts`, `overlay`, `providers`.
- `docs/client/interface/sections/localization.md` — любой видимый текст и accessibility label идут через Locale, без hardcoded строк.
- `docs/client/audio/sections/ui-audio.md` и `docs/client/interface/index.md` — звук и haptic как часть обратной связи.

Перед созданием нового компонента проверь `src/app/shared/components` (atoms, elements, ui, interaction, effects, widgets) и существующие presets/contracts в `src/app/shared/styles`.

## Принципы игрового UI (кратко)

Подробно — в `references/game-ui.md`.

- Это игра, а не SaaS-панель: никаких дашбордов из одинаковых карточек.
- Игровое поле важнее интерфейса: во время матча HUD минимален, центр экрана свободен.
- Экраны и модалки — это стек: открыт верхний, только он принимает ввод, «назад» возвращает фокус нижнему.
- У каждого контрола есть только нужные ему состояния, и они различимы без hover.
- Touch, мышь и клавиатура — равноправные способы ввода. Геймпад не считается поддержанным, пока это не проверено.
- Мобильная версия — не уменьшенный Desktop: перестраивай композицию, если она перестаёт быть удобной.

Художественное направление и анти-шаблоны — `references/art-direction.md`.
Платформы, размеры и проверка адаптивности — `references/platforms.md`.
Состояния контролов, motion и обратная связь — `references/interaction.md`.

## Визуальная проверка

Запускается по правилу «Визуальная проверка» из `AGENTS.md`: перед запуском спроси пользователя, проверить самому или он посмотрит сам. Если проверку не делали — так и напиши в отчёте. Как проверять, если проверка нужна:

1. Запусти dev-сервер (`.claude/launch.json` → `web-dev`, или `npm run dev`).
2. Сделай скриншоты в landscape-размерах: `2560×1318` (reference), `1920×1080`, `1280×720`, телефон `844×390`, планшет `1180×820`.
3. Проверь светлую и тёмную тему.
4. Проверь: ничего не обрезано и не перекрыто, safe area соблюдена, текст читается, фокус виден, длинные переводы не ломают раскладку.
5. Сравни с утверждённым макетом или описанием, если он есть. Найденные расхождения исправь и проверь снова.
6. В отчёте честно укажи, что проверено, а что нет (например, реальное устройство или Electron).

## Связь с другими skills

- `visual-review` — аудит и доводка уже готового экрана (отчёт, P0–P3).
- `visual-asset-design` — иконки, SVG, курсоры, иллюстрации для экрана.
- `ui-animation` — реализация и проверка анимаций и переходов.
- `platform-bridge` — когда решение зависит от платформы (safe area, haptic, fullscreen, ориентация).

Не запускай их автоматически для каждой задачи — подключай, когда работа действительно уходит в их область.

## Общение

Общайся по-русски. Критически оценивай и текущие решения, и свои предложения. Обосновывай рекомендации, не выдавай вкус за факт, отделяй гипотезы от требований и дизайн от реализации. Если пользователь просит визуализацию и есть подходящий инструмент — сделай её, но не выдавай концепт за точную спецификацию.
