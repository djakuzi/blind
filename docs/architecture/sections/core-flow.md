# Архитектура и core-flow

Раздел описывает устройство `src/core`: базовые переиспользуемые инструменты, правила зависимостей и назначение `core`-слоя в проекте.

## Назначение `src/core`

`core` - это инфраструктурный слой проекта.

Он нужен для того, чтобы:

- собирать базовые переиспользуемые утилиты;
- изолировать работу с внешними платформенными API;
- хранить типизированные media-registry и единый API доступа к ним;
- не тащить прямые зависимости на `Capacitor` и подобные SDK в `app`-слой;
- иметь одну точку замены реализации, если платформенный механизм меняется.

`core` не должен становиться местом для экранной логики, feature-сценариев или предметных правил игры.

## Назначение папок в `src/core`

### `lib`

Слой базовых утилит и простых преобразований.

Здесь лежат небольшие переиспользуемые функции, которые:

- не завязаны на конкретный экран;
- не знают про `Vue`, роутинг и app-flow;
- не зависят от платформенных SDK;
- могут использоваться в разных частях проекта.

Примеры модулей:

- `lib/boolean`
- `lib/array`

Такие модули должны оставаться простыми, предсказуемыми и максимально независимыми.

### `tool`

Слой инфраструктурных оберток над внешними API, browser/runtime механизмами и native-интеграциями.

`tool` нужен, чтобы прикладной код не обращался напрямую к низкоуровневым SDK.

Примеры модулей:

- `tool/storage` - единая работа с сохранением данных через `Capacitor Preferences`;
- `tool/system` - единая работа с системным `text zoom` через `Capacitor Text Zoom` и прочие механики;
- `tool/audio` - низкоуровневое управление preload, playback, loop, mute и unload через native audio API;
- `tool/input` - единая работа с pointer capabilities и media-query возможностями устройства.

Если в проекте меняется способ хранения, чтения системных настроек, воспроизведения аудио или другой платформенный механизм, изменения должны по возможности концентрироваться внутри `core/tool`.

### `media`

Слой типизированных media-registry и доступа к ассетам проекта.

Он не воспроизводит звук и не управляет UI. Его задача - скрыть generated-структуры и дать остальному проекту стабильный API получения media-ресурсов.

Текущие модули:

- `media/audio` - реестр аудио, доступ через `MediaAudio`;
- `media/icons` - реестр SVG-иконок, доступ через `MediaIcons`.

Оба модуля используют одинаковый принцип структуры:

```text
<media>/
├── index.ts
├── tool.ts
├── const.ts
└── type.ts
```

Где:

- `index.ts` - публичная точка входа и namespace API;
- `tool.ts` - ручной API доступа к данным;
- `const.ts` - generated registry;
- `type.ts` - generated типы registry.

Generated-файлы обновляются соответствующими генераторами и не должны вручную превращаться в место прикладной логики.

Для аудио:

```ts
MediaAudio.getAudio('sfx.interaction.hold-complete');
MediaAudio.getAudioGroup('sfx.interaction');
```

`MediaAudio` отвечает только за получение описания ассета или группы. Низкоуровневое воспроизведение остается в `ToolAudio`.

В Vue/app-слое стандартной точкой работы со звуком является `useAudio`:

```text
Vue component
    ↓
useAudio(audioId)
    ↓
MediaAudio
    ↓
ToolAudio
    ↓
NativeAudio
```

Компонентам не нужно самостоятельно резолвить `MediaAudio.getAudio(...)` перед обычным playback, если задача решается через `useAudio`.

Для иконок:

```ts
MediaIcons.getIcon(group, icon, theme);
```

`MediaIcons` скрывает generated registry и соглашение о themed-вариантах `Dark` / `Light`. UI-компоненты должны использовать публичный API, а не читать `ICONS_ASSETS` напрямую.

### `http`

Слой универсального HTTP transport.

Здесь находится инфраструктура для сетевых запросов, которая не знает про конкретные предметные API приложения:

- `HttpClient` - базовый клиент запросов;
- `HttpError` - единый формат HTTP-ошибок;
- `pipeline` - последовательность middleware для подготовки request, fetch, abort/timeout, parsing response и обработки ошибок;
- `helpers` - низкоуровневые HTTP-преобразования.

`core/http` отвечает только за транспортный механизм. Он не должен знать про доменные сущности, endpoints конкретной предметной области, Vue, Pinia или app-flow.

Граница ответственности:

- `core/http` - универсальный HTTP transport;
- `app/shared/api` - конкретные клиенты приложения, например `apiClient`;
- `app/domain/*/api` - предметные API конкретного домена.

Domain API не должен напрямую работать с `fetch`, если задачу можно решить через `app/shared/api` и `core/http`.

### `app`

Слой базовых механизмов запуска приложения.

`core/app/setup` содержит инфраструктуру setup lifecycle:

- контракт setup-задач;
- runner фаз `preMount` и `postMount`;
- runtime-state blocking setup;
- retry API для recoverable blocking setup;
- reactive API `useSetup`.

Blocking post-mount setup использует общий async-status из `core/types/status`:

```text
pending
loaded
error
```

Runner хранит registry blocking setup только как runtime-механизм текущего запуска приложения. Он не знает о loader, Pinia stores или конкретных системах Blind.

`isReady` вычисляется из runtime-state: post-mount должен быть начат, а все blocking setup должны иметь статус `loaded`.

`retryPostMountSetup(setupKey)` повторно запускает только blocking setup, который находится в `error`.

Setup-механизм в `core/app` не должен знать, какие конкретно системы Blind участвуют в setup. Состав приложения и setup языка, темы, масштаба или platform presentation остаются в `src/app/setup`.

## Принцип устройства `tool`-модулей

Каждый `tool`-модуль может быть разложен на простые части:

- `tool.ts` - публичные функции модуля;
- `helpers.ts` - локальные вспомогательные функции;
- `type.ts` - локальные типы, если они действительно нужны;
- `const.ts` - локальные константы, если они используются в нескольких файлах;
- `index.ts` - публичная точка входа.

Внутренняя логика, которая не является частью публичного API, должна по возможности оставаться в `helpers.ts` или других внутренних файлах, а не раздувать `tool.ts`.

Такой модуль должен давать проекту понятный API и скрывать детали конкретной платформенной реализации.

## Правила зависимостей

### Общий принцип

`core` должен оставаться более базовым слоем, чем другие директории.

Это означает:

- `core` не должен зависеть от других директорий приложения;
- `tool` может использовать внешние SDK - именно в этом его задача;
- `media` может импортировать статические ассеты из `src/assets`, но не должен зависеть от Vue-компонентов или app-flow;
- `http` может использовать browser/runtime HTTP primitives, но не должен зависеть от app/domain слоев;
- `app` может использовать framework primitives, необходимые базовым механизмам запуска приложения, но не должен зависеть от конкретных app setup-модулей.

## Базовые правила

1. Все платформенные интеграции должны по возможности проходить через `core/tool`.
2. Если одна и та же низкоуровневая интеграция нужна в нескольких местах, не стоит дублировать прямые вызовы SDK по проекту.
3. `core/lib` должен оставаться простым и независимым.
4. `core/tool` должен скрывать детали реализации и отдавать наружу понятный API.
5. `core/media` должен скрывать generated registry за публичными `Media*` API.
6. `core/http` должен оставаться универсальным транспортом без знания о доменных endpoints.
7. `core/app` содержит базовые механизмы запуска приложения и не знает состав конкретных setup-модулей Blind.
8. Если появляется новый важный паттерн в `core`, его стоит фиксировать в документации.
