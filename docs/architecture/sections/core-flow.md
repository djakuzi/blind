# Архитектура и core-flow

Раздел описывает назначение `src/core`, границы platform-слоя и основные правила зависимостей.

## Назначение `src/core`

`core` содержит базовую инфраструктуру, которая переиспользуется разными частями приложения и не должна зависеть от экранных сценариев или игровой логики.

Основные задачи:

- общие утилиты;
- platform-интеграции;
- media-registry;
- HTTP transport;
- базовые механизмы запуска приложения.

## Основные части

### `lib`

Небольшие независимые утилиты и преобразования.

`lib` не должен зависеть от Vue, app-flow, игровых правил или платформенных SDK.

### `platform`

Слой работы с Web, Capacitor и Electron.

Он состоит из четырех основных частей:

- `adapter` — выбор реализации под текущий runtime;
- `runtime` — определение среды и общая инфраструктура среды;
- `tool` — публичные platform-инструменты и их реализация;
- `type.ts` — общие platform-типы результата, значения и подписки.

### `platform/runtime`

`runtime` отвечает только за саму среду выполнения.

Здесь допустимы:

- определение `web`, `mobile` и `desktop`;
- определение конкретной платформы;
- доступ к Electron bridge;
- общие helpers среды, которые не принадлежат одному конкретному инструменту.

`runtime` не реализует Audio, Storage, Filesystem, View и другие инструменты.

Главная граница зависимостей:

- `tool -> runtime` разрешено;
- `runtime -> tool` запрещено.

Desktop runtime может использовать типы и конфигурацию Electron bridge, потому что это контракт среды, а не логика конкретного инструмента.

### `platform/tool`

`tool` является владельцем конкретного platform-инструмента.

Tool отвечает за:

- публичный API;
- общую семантику инструмента;
- состояние и orchestration, если они нужны;
- выбор platform adapter;
- platform-specific реализацию через adapters;
- локальные helpers и engines конкретного инструмента.

Текущие инструменты:

- Audio;
- Filesystem;
- Input;
- Storage;
- System;
- Vibration;
- View.

Platform-specific код должен оставаться внутри соответствующего Tool, если он существует только для реализации этого инструмента.

Например Web Audio engine относится к Audio, OPFS — к Filesystem, gamepad rumble — к Vibration.

### Структура Tool

Обычно Tool содержит:

- `index.ts` — публичную точку входа и выбор adapter;
- `tool.ts` — общий API, состояние и orchestration;
- `type.ts` — контракт Tool и adapter;
- `adapters` — реализации для нужных runtime;
- `helpers` — внутренние вспомогательные части;
- `engines` — более крупные внутренние реализации, если они действительно нужны;
- `const.ts` — общие константы инструмента.

Не каждый Tool обязан иметь все эти папки.

### Electron и Tool

Electron plugin предоставляет только ту desktop-функциональность, которая должна выполняться через Electron main/preload boundary.

Tool при этом остается владельцем самого инструмента.

Desktop adapter обращается к Electron capability через runtime bridge, когда ему нужна privileged desktop-операция.

Electron plugin не должен автоматически дублировать полный API Tool.

## `media`

`media` скрывает generated media-registry и предоставляет стабильный типизированный API доступа к ассетам.

Текущие модули:

- `media/audio` через `MediaAudio`;
- `media/icons` через `MediaIcons`.

Media-слой не отвечает за playback или UI-поведение. Например получение audio resource относится к `MediaAudio`, а воспроизведение — к `ToolAudio`.

## `http`

`core/http` — универсальный HTTP transport.

Он отвечает за запросы, middleware, timeout, parsing и общий формат ошибок, но не знает о предметных API приложения.

Конкретные API-клиенты и endpoints должны находиться выше по слоям приложения.

## `app`

`core/app` содержит базовые механизмы запуска приложения, включая setup lifecycle.

Он предоставляет инфраструктуру setup, но не должен знать состав конкретных setup-модулей Blind.

## Правила зависимостей

1. Прикладной код не должен напрямую обращаться к platform SDK, если для задачи существует `core/platform/tool`.
2. Реализация конкретного инструмента должна находиться в соответствующем Tool, а не в `runtime`.
3. `runtime` не должен импортировать `tool`.
4. Общий runtime helper имеет смысл только тогда, когда он описывает возможность среды и используется несколькими инструментами или самим runtime.
5. Instrument-specific helpers, engines и platform mappings остаются внутри соответствующего Tool.
6. Electron main/preload используется только для desktop-возможностей, которым действительно нужен Electron boundary.
7. Общая логика Tool не должна дублироваться между platform adapters, если ее можно безопасно переиспользовать внутри самого Tool.
8. Если меняется архитектурная граница или публичный platform API, документацию нужно обновлять вместе с кодом.
