# Локализация интерфейса

Как устроены переводы: два уровня locale, контракт, выбор и смена языка, правила для текста в компонентах.

## Два уровня

| | Static Locale | Full Locale |
|---|---|---|
| Назначение | инфраструктурный UI до готовности основной локализации: запуск, загрузка, критические ошибки | все пользовательские тексты после инициализации |
| Источник | встроен в приложение, без загрузки | любой: bundled, cache, API — UI об этом не знает |
| Объём | минимальный | полный контракт |

1. Static Locale не становится вторым набором переводов: обычный UI — только в Full Locale.
2. Fallback Static Locale и Full Locale — независимые понятия.
3. Инфраструктура Static Locale (реестр, нормализация, fallback) не знает о store. Связь с текущим языком собирает feature.

## Граница источника

```text
источник / transport / cache → store языка → Locale contract → UI
```

UI не обращается к конкретному JSON, endpoint или пути файла.

## Locale contract

Контракт типизирован и построен по смыслу текста, а не по месту хранения.

| Категория | Что хранит |
|---|---|
| общие тексты | то, что повторяется в разных местах («Назад», «Отмена») — не дублируется по экранам |
| тексты экранов | группируются по экрану: `экран → подэкран → ui / modals / states` |
| значения настроек | значение отдельно от названия настройки: «Тема» ≠ «Тёмная» |
| сущности | название, описание, подписи; идентификатор и данные — в domain |
| шаблоны | строки с подстановкой: `"{count} players"` |

## Выбор языка

Приоритет:

```text
явный выбор пользователя → язык окружения → язык по умолчанию
```

1. Определённый автоматически язык не сохраняется как выбор пользователя — иначе смена языка системы перестанет работать.
2. Код языка нормализуется перед сравнением: точная локаль → базовый язык → fallback (`en_US` → `en-us` → `en`).
3. Отдельный перевод для каждого региона не нужен, если поддержан базовый язык.

## Инициализация

| Фаза | Что происходит |
|---|---|
| `preMount` | определяется предпочтительный язык из настроек или окружения; Full Locale ещё может быть недоступен |
| `postMount` (blocking) | определены поддерживаемые языки, активный язык и валидный Full Locale |

1. Инвариант: язык инициализирован → есть активный язык и Full Locale.
2. Route UI не рендерится раньше этого инварианта. До него можно показывать Static Locale.

## Fallback

```text
язык:   предпочтительный → базовый → поддерживаемый по умолчанию
данные: предпочтительный источник → валидный локальный → источник по умолчанию
```

Отказ одного источника не должен оставлять UI частично инициализированным.

## Cache и версии

1. Cache — оптимизация и источник восстановления, не часть контракта.
2. При версиях: совместимая версия в cache переиспользуется, несовместимая обновляется.
3. Смена формата хранения не требует изменений UI, пока контракт тот же.

## Смена языка

```text
определить язык → подготовить валидный locale → сохранить выбор
→ активировать язык и locale → обновить document и платформу
```

1. Язык не активируется раньше, чем готов его locale.
2. Подготовка не удалась — остаётся текущий рабочий locale.
3. Интерфейс обновляется без перезагрузки приложения.

## Названия языков

1. Название показывается на текущем языке интерфейса через `Intl.DisplayNames`, если он доступен.
2. Fallback — собственное название языка из metadata.
3. Полный список названий всех языков в каждом locale не хранится.

## Множественное число и шаблоны

1. Категория формы определяется через `Intl.PluralRules`. Locale хранит формы, код выбирает нужную, обязательная форма — `other`.
2. Свои правила для каждого языка не пишутся.
3. Текст с runtime-значениями хранится шаблоном и собирается централизованным helper или formatter.

## Текст в переиспользуемых компонентах

Переиспользуемый компонент не содержит пользовательского текста по умолчанию. Текст приходит от вызывающего кода уже переведённым.

```ts
// Неправильно
withDefaults(defineProps<PropsAppExample>(), { text: 'Loading' });

// Правильно: текст передаёт вызывающий код из locale
<AppExample :text="locale.loading" />
```

Это касается и невидимого текста: placeholder, `aria-label`, описания доступности, empty state, ошибки, tooltip, `alt` для не декоративного изображения. Пустое значение допустимо, если отсутствие текста корректно по смыслу.

## Добавление текста

1. Определить смысловую категорию.
2. Обновить тип контракта.
3. Добавить значение во все языки — обязательный ключ только в одном языке недопустим.
4. Передать перевод до компонента и убрать захардкоженный текст.
5. Проверить смену языка и тексты доступности.
6. Запустить lint и сборку.

## Добавление языка

1. Зарегистрировать язык в поддерживаемых.
2. Полностью реализовать контракт, указать корректный код и fallback-название.
3. Проверить начальный выбор, смену на лету, форматирование, cache и версии.
4. Static Locale для нового языка нужен, только если инфраструктурный UI на нём требуется до загрузки Full Locale. Тогда: полный контракт Static Locale, сохранённый fallback, проверка запуска без Full Locale.

## Нельзя

1. Хранить переводы в domain-моделях и технических константах.
2. Привязывать UI к transport или месту хранения переводов.
3. Использовать Static Locale как основной источник после запуска.
4. Маскировать нарушение контракта тихим fallback вроде пустой строки.
5. Переносить зависимую от store композицию в shared-инфраструктуру.
