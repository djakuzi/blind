# Запуск приложения

Как приложение запускается: фазы setup, готовность, глобальный loader, ошибки и повтор.

## Общий поток

```text
create app → Pinia → setup registry
→ preMount (по очереди)
→ router
→ mount
→ postMount
   ├── blocking   — отслеживается: pending / loaded / error
   └── background — не влияет на готовность
→ все blocking = loaded → isReady → route UI
```

1. `ProviderLoaderApp` монтируется сразу; `RouterView` и `ProviderSessionJoin` — только при `isReady`.
2. Если blocking-задача упала, приложение остаётся смонтированным, route UI закрыт, loader показывает ошибку и даёт повторить.

## Фазы setup

| Фаза | Когда | Для чего |
|---|---|---|
| `preMount` | до `app.mount()` | предпочтения, системные настройки, окружение платформы, визуальные параметры без мигания |
| `postMount` | после mount | остальная инициализация |

Задача `postMount` имеет режим:

| Режим | Влияние |
|---|---|
| `blocking` | route UI не открывается, пока задача не завершится |
| `background` | запускается после mount, на готовность не влияет |

Фаза отвечает на вопрос «когда запускать», режим — «влияет ли на готовность». Асинхронность — не отдельная фаза.

## Устройство setup

| Часть | Путь | Назначение |
|---|---|---|
| lifecycle | `src/core/app/setup/lifecycle` | контракт, runner, состояние, `useSetupLifecycle` |
| registry | `src/app/setup` | какие setup-модули участвуют |
| модули | `src/app/setup/<область>` | setup конкретных систем (интерфейс, платформа) |

1. Lifecycle не знает о конкретных системах приложения.
2. Registry — точка композиции, набор модулей может меняться.
3. Модуль реализует `preMount`, `postMount` или обе фазы.
4. Модуль вызывает публичный API системы, а не собирает её внутренние шаги сам:

```text
setup-модуль → API системы → store / domain / core
```

5. UI получает состояние через `useSetupLifecycle`, не завися от runner.

## Готовность

1. Каждая blocking-задача имеет статус `pending`, `loaded` или `error`.
2. `isReady` — postMount начался и все blocking-задачи `loaded`. Нет blocking-задач — готово сразу.
3. Хотя бы одна `pending` — приложение запускается. Хотя бы одна `error` — route UI закрыт до восстановления.
4. Готовность setup и активность loader — разные вещи: loader работает в любой момент и не делает запущенный UI «неготовым».

## Повтор упавшей задачи

`retryPostMountSetup(setupKey)` — только для blocking-задачи со статусом `error`.

```text
error → действие пользователя → retryPostMountSetup
→ pending → run()
   ├── успех → loaded (если все loaded — isReady = true)
   └── ошибка → error
```

## Глобальный loader

Setup-модуль может зарегистрировать loader resource, если его загрузку нужно показать пользователю.

### Resource и scope

1. Resource — единственный источник своего состояния: `pending → loaded` или `pending → error → retry → pending`. Ошибка хранится в resource и может содержать действие для восстановления.
2. Scope группирует resources и может иметь заголовок. Завершённость scope вычисляется по resources.
3. Runner не зависит от loader.

### Progress

| Режим | Поведение |
|---|---|
| `determinate` | progress = загруженные / все; при завершении полоса доходит до 100% |
| `indeterminate` | процент неизвестен, бесконечное движение |

1. Если в сессии хотя бы один scope `indeterminate`, вся сессия остаётся `indeterminate` до скрытия.
2. Запуск языка — `determinate`, ручная смена языка — `indeterminate`.

### Показ и скрытие

1. Loader появляется сразу при первом `pending` или `error`.
2. Действует минимальное время показа, отсчитанное от момента появления: быстрая операция ждёт остаток, долгая скрывается сразу после завершения.
3. Ошибка удерживается до конца анимации ухода. Явная отмена убирает scope без возврата к загрузке.

### Что показывается

```text
есть error   → состояние ошибки (первая из нескольких; после retry — следующая)
есть pending → progress
все loaded   → завершить показ и скрыть
```

1. Provider выбирает состояние, блокирует ввод в UI под loader и держит фокус внутри loader, пока сессия активна.
2. Завершённые scopes хранятся до конца анимации ухода, потом provider их очищает.
3. Widget loader только отображает данные от provider и не обращается к store.
4. Indeterminate-полоса не имеет `aria-valuenow` и при reduced motion остаётся статичной.

## Ошибки

| Тип | Как обрабатывается |
|---|---|
| recoverable blocking | задача остаётся `error`, route UI закрыт, есть способ повторить |
| fallback | если безопасный fallback есть (особенно в `preMount`), применить и продолжить |
| fatal `preMount` | loader ещё недоступен; ошибку обязан зафиксировать `setupApp().catch(...)` |
| background | логируется, UI не блокирует |

Критическая blocking-ошибка не может тихо перевести приложение в `isReady`.
