# Правила AGENTS

Что писать в `AGENTS.md` и как его поддерживать.

## Назначение

`AGENTS.md` — входная инструкция для coding agents. Он направляет к источнику истины, а не заменяет документацию.

1. Коротко объяснить, как работать с проектом.
2. Подсказать, какие документы читать под задачу.
3. Зафиксировать критичные ограничения проекта.
4. Сказать, что делать при нехватке информации или расхождении кода и документации.

## Где лежит и кто читает

| Файл | Что в нём |
|---|---|
| `AGENTS.md` в корне | общие правила и карта репозитория |
| `apps/<приложение>/AGENTS.md` | правила приложения: пути, таблица «задача → документ», skills |

1. Агент читает `AGENTS.md` от корня до папки, из которой запущен. Запуск из `apps/<приложение>` даёт общие правила и правила этого приложения — без правил других приложений.
2. Codex и другие агенты ищут `AGENTS.md` сами, поэтому файлы не переносятся.
3. Claude Code читает их через `.claude/CLAUDE.md` рядом с каждым `AGENTS.md`, с импортом `@../AGENTS.md`.
4. Правило нужно всем приложениям — в корневой `AGENTS.md`, одному — в `AGENTS.md` приложения. В файлах конкретного агента — только переходники и настройки.

## Что писать

1. Роль файла.
2. Что сделать перед изменениями и какой минимум контекста собрать.
3. Где брать информацию под тип задачи — ссылки на `docs`.
4. Правило смотреть соседние реализации.
5. Критичные ограничения архитектуры, именования, процесса.
6. Что делать при расхождении и при нехватке информации.

## Чего не писать

1. Пересказ архитектуры, code style или процесса — вместо этого ссылка на `docs`.
2. Временные договорённости по одной задаче.
3. Повтор ограничений, уже подробно описанных в `docs`.

`AGENTS.md` не заставляет перечитывать всю документацию: он помогает выбрать нужные разделы.

## Как писать

1. Коротко, с понятными заголовками, по [Правилам документации](../../workflow/rules/docsRule.md).
2. Инструкция применима до начала работы: «Если задача затрагивает CSS — открыть `cssStyle.md`», а не «Делай правильно».
3. Текст устойчив во времени и не привязан к деталям одной задачи.

| Хорошо | Плохо |
|---|---|
| «Если код и документация расходятся — отметить и предложить правку» | «Ориентируйся по ситуации» |
| «Перед изменением кода посмотреть соседние реализации» | «Если что, сам решишь» |
