# Code Style

Правила стиля кода в `blind`.

Документ фиксирует базовые соглашения проекта заранее, пока кодовая база еще небольшая. Это не описание уже сложившегося legacy, а целевой стиль, которого стоит придерживаться при развитии проекта.

## 1. Общие принципы

1. Код пишется так, чтобы его можно было быстро прочитать, понять и безопасно изменить через несколько месяцев.
2. Понятность важнее сокращений, умных трюков и избыточной абстракции.
3. Любая сущность должна иметь одно очевидное назначение.
4. Если решение можно сделать проще без потери качества, выбирается более простое решение.
5. Перед добавлением новой абстракции стоит убедиться, что она действительно решает повторяющуюся проблему.
6. Временные решения допустимы только тогда, когда они явно обозначены и понятны команде.

## 2. Общая структура проекта

Проект делится на несколько основных областей:

- `src/app` - прикладной слой, экраны, роутинг, провайдеры, layout, глобальные стили и store.
- `src/shared` - переиспользуемые утилиты и низкоуровневые общие модули без привязки к конкретному экрану.
- `src/config` - конфигурация приложения, окружения и общие настройки.
- `docs` - внутренняя документация проекта.

Правила распределения кода:

1. Код, завязанный на бизнес-логику приложения, должен лежать в `app`.
2. Код, который не знает про конкретный экран, модуль или фичу, должен лежать в `shared`.
3. Конфигурация окружения, адреса API, флаги платформ и настройки рантайма должны лежать в `config`.
4. Если модуль сложно отнести в `shared`, скорее всего, ему место в `app`.

## 3. Именование директорий

1. Имена директорий пишутся в `camelCase`.
2. Имя директории должно отражать функциональную область, а не техническую случайность.
3. Не стоит использовать слишком общие имена вроде `helpers`, `misc`, `common2`, `new`, `temp`.
4. Если директория содержит UI-компоненты, ее имя должно описывать область применения: `buttons`, `modals`, `typography`, `containers`.

Примеры:

- `app`
- `shared`
- `routes`
- `settings`
- `orderHistory`
- `ui`

## 4. Именование файлов

1. Обычные файлы пишутся в `camelCase`.
2. Vue-компоненты пишутся в `PascalCase`.
3. Имя файла должно совпадать с главной сущностью внутри файла.
4. Не стоит использовать сокращения, если они не являются общепринятыми в проекте.

Рекомендуемые суффиксы:

- `.vue` - Vue-компоненты
- `.ts` - логика, утилиты, конфигурация
- `.store.ts` - Pinia store
- `.service.ts` - сервисы
- `.const.ts` - константы
- `.types.ts` - типы
- `.model.ts` - модели

Примеры:

- `AppButton.vue`
- `game.store.ts`
- `route.const.ts`
- `api.service.ts`
- `user.types.ts`

## 5. Именование переменных, функций и констант

1. Переменные и функции пишутся в `camelCase`.
2. Константы верхнего уровня пишутся в `UPPER_SNAKE_CASE`.
3. Булевы значения должны иметь читаемые префиксы `is`, `has`, `can`, `should`.
4. Обработчики событий начинаются с `handle`.
5. Фабрики и конструкторы значений могут начинаться с `create`.
6. Функции чтения состояния могут начинаться с `get`.
7. Функции проверки могут начинаться с `is`, `has`, `can`.

Примеры:

- `isLoading`
- `hasAccess`
- `canStartGame`
- `handleClick`
- `createToast`
- `getCurrentRoute`

## 6. Именование типов

1. `type`, `interface`, `enum` и `class` пишутся в `PascalCase`.
2. Название типа должно описывать сущность, а не техническую форму.
3. Для props компонента используется имя `Props`.
4. Для emit-событий допустимо использовать отдельный type или inline-сигнатуры, если они короткие.
5. Не стоит добавлять префиксы `I` для интерфейсов.

Примеры:

- `type ThemeMode = 'light' | 'dark'`
- `interface Props`
- `interface GameState`
- `type RouteName`

## 7. Импорты

1. Импорты должны быть короткими и читаемыми.
2. Для файлов из `src` используется алиас `@`.
3. Type-импорты пишутся через `import type`.
4. Неиспользуемые импорты должны удаляться сразу.
5. Не стоит собирать в одном файле хаотичные относительные пути вида `../../../../../`.

Рекомендуемый вид:

```ts
import { createApp } from 'vue'
import { createPinia } from 'pinia'

import App from '@/App.vue'
import { router } from '@/app/routes/route'
import type { ThemeMode } from '@/config/types'
```

## 8. Правила для TypeScript

1. TypeScript используется как основной язык проекта.
2. Предпочтение отдается явным и читаемым типам.
3. Типы должны помогать разработке, а не усложнять код без пользы.
4. `any` не используется без явной причины.
5. Если тип можно выразить проще, выбирается более простая запись.
6. `as` используется аккуратно и только когда тип действительно невозможно вывести безопаснее.
7. Для словарей и фиксированных наборов значений используется `as const`.
8. Для объединений значений лучше использовать литеральные union-типы.

Пример:

```ts
export const THEME_MODE = {
  light: 'light',
  dark: 'dark',
  system: 'system',
} as const

export type ThemeMode = (typeof THEME_MODE)[keyof typeof THEME_MODE]
```

## 9. Правила для Vue-компонентов

1. Во всех новых компонентах используется `<script setup lang="ts">`.
2. Один компонент должен решать одну визуальную или логическую задачу.
3. Компоненты не должны знать больше, чем им нужно знать.
4. Сложную бизнес-логику не стоит держать внутри больших `.vue` файлов, ее лучше выносить в отдельные модули.
5. Props описываются через `interface Props`.
6. Значения по умолчанию задаются через `withDefaults`, если это действительно нужно.
7. События описываются через `defineEmits`.
8. Если компонент является только оберткой над layout или primitive UI, это должно быть видно из его API.

Рекомендуемая структура компонента:

```vue
<script setup lang="ts">
import type { RouteLocationRaw } from 'vue-router'

interface Props {
  title: string
  to?: RouteLocationRaw
  disabled?: boolean
}

const props = withDefaults(defineProps<Props>(), {
  disabled: false,
})

const emit = defineEmits<{
  click: []
}>()

function handleClick() {
  if (props.disabled) {
    return
  }

  emit('click')
}
</script>

<template>
  <button type="button" @click="handleClick">
    {{ title }}
  </button>
</template>
```

## 10. Props, emits и composables

1. Props должны быть минимальными и понятными.
2. Не стоит передавать в компонент лишние данные на будущее.
3. Названия props должны описывать смысл, а не внутреннюю реализацию.
4. События должны описывать факт, а не реализацию.
5. Composable-функции начинаются с `use`.
6. Composable должен инкапсулировать повторяющуюся реактивную логику, а не быть просто папкой для случайного кода.

Хорошо:

- `visible`
- `disabled`
- `title`
- `useTheme`
- `useGameSession`

Плохо:

- `data`
- `item`
- `propsData`
- `handleLogic`

## 11. Состояние и store

1. Глобальное состояние хранится только там, где оно реально нужно нескольким частям приложения.
2. Локальное состояние должно оставаться локальным для компонента.
3. Store должен быть небольшим и понятным.
4. Один store отвечает за одну предметную область.
5. Store не должен превращаться в второй backend внутри клиента.
6. Названия store-файлов оформляются как `[domain].store.ts`.

Примеры:

- `game.store.ts`
- `settings.store.ts`
- `user.store.ts`

## 12. Роутинг

1. Все маршруты должны иметь предсказуемые имена и структуру.
2. Константы маршрутов и их имена должны храниться централизованно.
3. Если маршрут относится к отдельной области, его можно выносить в `routes/sections`.
4. Не стоит дублировать строковые пути по всему проекту вручную.

## 13. Утилиты и shared-код

1. В `shared` попадает только по-настоящему переиспользуемый код.
2. Если утилита используется в одном месте и тесно связана с доменом, ей лучше оставаться рядом с этим доменом.
3. Утилиты должны быть маленькими и предсказуемыми.
4. Одна утилита должна решать одну задачу.
5. Название утилиты должно говорить, что она делает.

Примеры:

- `toModules`
- `toBooleanModules`
- `isEmptyArray`

## 14. Комментарии

1. Комментарии пишутся только там, где код нельзя сделать достаточно понятным самим кодом.
2. Комментарии должны объяснять причину, ограничение или нетривиальное решение.
3. Не стоит комментировать очевидные действия.
4. Если комментарий устарел, его нужно обновить или удалить.

Хорошо:

```ts
// iOS Safari может неверно учитывать safe area в embedded webview.
```

Плохо:

```ts
// Увеличиваем счетчик на 1.
counter += 1
```

## 15. Форматирование и длина конструкций

1. Код должен быть визуально компактным, но не сжатым в одну строку.
2. Если выражение трудно читать в одну строку, его следует перенести.
3. Глубокая вложенность нежелательна.
4. Лучше использовать early return, чем большие вложенные `if`.
5. Один файл не должен бесконтрольно разрастаться. Если в файле несколько разных ответственностей, их стоит разделить.

## 16. Обработка ошибок

1. Ошибки не должны замалчиваться.
2. Если ошибка ожидаемая, код должен явно это показывать.
3. Пользовательские сообщения об ошибках должны быть понятными.
4. Технические подробности не должны утекать в UI без необходимости.
5. Любая ветка с ошибкой должна иметь осмысленное поведение.

## 17. Стили и CSS

1. Глобальные стили лежат в `src/app/styles`.
2. `core` отвечает за базовые стили платформы: reset, fonts, base.
3. `tokens` отвечает за дизайн-токены проекта.
4. CSS-классы пишутся в `kebab-case`.
5. Для компонентов используется BEM-подход, если компонент имеет заметную внутреннюю структуру.
6. Все публичные CSS variables проекта имеют префикс `--app-`.
7. Компоненты должны опираться на токены, а не на случайные `hex`, `px` и `z-index`.
8. Цвета, отступы, радиусы, слои и типографика должны по возможности задаваться через токены.

Примеры:

- `.game-screen`
- `.game-screen__header`
- `.game-screen--paused`
- `--app-color-text-primary`
- `--app-layer-modal`
- `--app-font-size-16`

## 18. Темизация

1. Тема должна управляться централизованно.
2. Theme-aware значения должны храниться в токенах.
3. Компоненты не должны знать конкретные hex-цвета темы.
4. Компонент должен использовать семантический токен, а не вычислять тему самостоятельно.

Хорошо:

```css
color: var(--app-color-text-primary);
background: var(--app-color-surface-primary);
```

Плохо:

```css
color: #ffffff;
background: #141416;
```

## 19. Документация и самодокументируемость

1. Новый код должен быть понятен без необходимости читать автора в чате.
2. Если модуль сложный, для него должна появиться короткая документация в `docs`.
3. Архитектурные решения лучше фиксировать сразу, пока они не забылись.
4. Названия файлов, функций и типов являются первой линией документации.

## 20. Чего стоит избегать

1. Магических чисел и строк без объяснения происхождения.
2. Огромных универсальных компонентов на все случаи.
3. Преждевременной абстракции.
4. Дублирования одинаковой логики в нескольких местах.
5. Неявных сайд-эффектов.
6. Слишком общих имен вроде `data`, `value`, `item`, `temp`, `helper`.
7. Смешивания бизнес-логики, UI-логики и инфраструктурного кода в одном месте.

## 21. Базовый ориентир качества

Перед добавлением кода стоит проверить:

1. Понятно ли из названия, что делает сущность.
2. Находится ли код в правильном слое проекта.
3. Нет ли уже похожей логики в проекте.
4. Можно ли упростить решение без потери пользы.
5. Используются ли существующие токены, типы и соглашения проекта.
6. Сможет ли другой разработчик быстро продолжить работу без устных пояснений.

Этот документ будет уточняться по мере роста проекта. Если фактическая практика команды начнет отличаться от описанных правил, документ должен обновляться вместе с кодовой базой.
