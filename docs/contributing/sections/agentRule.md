# Правила AGENTS

Раздел описывает, что должно быть написано в `AGENTS.md` и как его оформлять.

`AGENTS.md` - это входной файл-инструкция для coding agents, которые начинают работу с репозиторием.

## Назначение файла

1. Коротко объяснить агенту, как работать с проектом.
2. Указать, как выбирать документы под конкретную задачу.
3. Зафиксировать самые важные проектные ограничения.
4. Подсказать, как действовать, если информации не хватает или правила расходятся.

`AGENTS.md` не должен заменять всю документацию проекта. Его задача - направить агента к источнику истины и зафиксировать базовые инварианты.

## Что должно быть в `AGENTS.md`

Обычно файл содержит:

1. Короткое описание роли файла.
2. Общие правила работы перед изменениями.
3. Минимальный контекст, который нужно собрать перед задачей.
4. Ориентир, из каких разделов документации брать информацию под разные типы задач.
5. Правило смотреть смежные реализации перед изменением кода.
6. Базовые ограничения по архитектуре, именованию или процессу, если они критичны.
7. Правило, как действовать при расхождении между кодом и документацией.
8. Правило, как действовать, если перед реализацией не хватает информации.

## Что не стоит писать в `AGENTS.md`

1. Не стоит дублировать целиком архитектурные документы.
2. Не стоит переписывать в него весь code style.
3. Не стоит копировать большие куски process-документации.
4. Не стоит складывать туда временные договоренности по одной задаче.
5. Не стоит превращать `AGENTS.md` в длинную энциклопедию проекта.
6. Не стоит перегружать файл повторяющимися ограничениями, если они уже подробно описаны в `docs`.

Если правило уже подробно описано в `docs`, в `AGENTS.md` лучше оставить короткую ссылку или краткий ориентир.

Важно: `AGENTS.md` не должен заставлять агента перечитывать всю документацию для каждой маленькой задачи. Он должен помогать выбрать релевантные разделы и расширять контекст только тогда, когда задача этого требует.

## Как писать `AGENTS.md`

1. Писать коротко и по делу.
2. Использовать понятные заголовки.
3. Разделять общие правила и ссылки на документацию.
4. Формулировать инструкции так, чтобы агент мог применить их до начала работы.
5. Сохранять текст устойчивым во времени и не привязывать его к случайным деталям одной задачи.
6. Если подробное правило уже есть в документации, в `AGENTS.md` лучше оставить короткую ссылку или ориентир, а не пересказ.

## Рекомендуемая структура

Пример простой структуры:

```md
# AGENTS

Этот файл является входной инструкцией для coding agents.

## Перед началом работы

1. Изучить затронутые файлы.
2. Определить затронутые слои проекта.
3. Прочитать документацию, связанную с этими слоями.
4. Посмотреть смежные реализации в том же слое или с похожей задачей.
5. Не придумывать новую архитектуру, если она уже описана.

## Минимум контекста

- понять задачу
- изучить затронутые файлы
- найти связанные разделы документации
- проверить локальные паттерны рядом с изменяемым кодом
- посмотреть похожие реализации, чтобы понять живой стиль проекта

## Где брать информацию

- по архитектуре - в `docs/architecture`
- по генераторам - в `docs/generators`
- по процессу разработки - в `docs/contributing`

## Если есть расхождение

1. Не переписывать проект целиком под документ.
2. Сообщить о расхождении.
3. Предложить точечное изменение.

## Если есть вопросы

1. Сначала составить короткий список вопросов или неясностей.
2. Потом либо задать их пользователю, либо найти ответ в документации, если это можно сделать надежно без догадок.
```

## Примеры хороших формулировок

- `Перед изменениями агент должен сначала изучить затронутые файлы и связанные с задачей разделы документации.`
- `Если задача затрагивает архитектуру, сначала нужно открыть разделы из docs/architecture.`
- `Если задача затрагивает CSS, нужно открыть docs/contributing/sections/cssStyle.md.`
- `Если задача затрагивает core API, нужно открыть docs/architecture/sections/core-flow.md.`
- `Если правило уже зафиксировано в документации проекта, не нужно придумывать альтернативу.`
- `Перед изменением кода агент должен посмотреть смежные реализации, если они есть.`
- `Документация задает правила, а соседний код показывает, как эти правила применяются в проекте.`
- `Если код и документация расходятся, агент должен отметить это и предложить безопасную правку.`
- `Если перед реализацией не хватает информации, агент должен сначала сформировать короткий список вопросов или неясностей.`
- `Если после изменения нужно обновить документацию, агент должен сообщить об этом пользователю и запросить разрешение на правку docs.`

## Примеры плохих формулировок

- `Делай все правильно.`
- `Ориентируйся по ситуации.`
- `Если что, сам решишь.`

Такие формулировки слишком расплывчаты и не помогают агенту принять конкретное решение.
